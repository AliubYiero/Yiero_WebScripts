# 0001 可更新消息与常驻豁免

- Status: accepted
- Date: 2026-11-09

## Context

`Message` 原先只有「发一条、到点自己消失」这一种生命周期：调用即建卡片，
`duration` 到点自动关闭，页面上最多同屏 3 条，超出时挤掉最早的那条。
没有「改一条已经在页面上的消息」，也没有「不自动消失」的概念。

长任务进度卡是第一个不满足于公开能力的使用者：一轮几分钟的加载，
希望**同一张卡**随进度改文案，结束时把类型改成成功或失败、再切成有限
时长让它自己收尾。用现有 API 只能退而求其次——连弹 N 条，彼此打断，
还会被 3 条上限挤掉最旧的那条，用户看到的是一串互相覆盖的提示。

本 ADR 记录这次扩展的两处取舍，以及一处**有意不做**的改动。这里只写
能力形状与理由，不写实现步骤；库的实现改动另有其票。

## Decision

### 用 `update` + `duration: 0`，不新增 `Message.loading()`

消息实例获得一个「可更新」入口：能改文案、改类型、改时长，改时长时从
那一刻重新开始计自动关闭。`duration: 0` 单独定义为**常驻**——不启动
自动关闭计时，除 `0` 外的取值仍受原有最小时长约束。位置在创建后固定，
不参与更新。

换句话说，「一条消息的生命周期」只有一套，只是这条生命周期中途可变、
且可以不设终点。

### 常驻消息豁免 3 条上限的淘汰，但仍计入条数

条数上限的淘汰只在**可被淘汰的消息**里挑最早的：常驻消息不动。但常驻
消息照常占用条数名额，所以它们是「占位不淘汰」。极端情况——同屏全是
常驻——不再强行关闭任何一条，接受同屏超过 3 条。

## Consequences

- 一个卡片可以从「加载中」走到「成功/失败」，全程只有一张卡，不会因为
  出现别的提示而被打断。
- 调用方拿到的实例在创建后仍然是同一个对象，状态变化通过更新表达，不需要
  自己记住「第几条是我发的」。
- 常驻消息不会被任何新消息顶掉，遇到「进度卡凭空消失」这类现象可以按
  bug 处理，而不是当作正常的淘汰行为。
- 页面消息总量仍有上界感：常驻消息计入条数，所以「还有几个名额」是可算
  的，不会因为常驻而不受控地增长。
- 同屏条数可能突破 3 条。这是明确接受的代价，不是遗漏：宁可多显示，也
  不静默清掉用户正在看的卡片。
- 常驻消息必须由调用方显式关闭，或者被更新成有限时长；忘记收尾就会一直
  留在页面上。
- 位置在创建后不可变，调用方不能在消息存续期间把它挪到别的位置。

## Alternatives considered

- **新增 `Message.loading()`**：语义上最贴近「进度卡」这个场景，调用方
  少写几行。但它会把一条消息的生命周期拆成两套——静态快捷键族
  （`success` / `warning` / `error` / `info`）与 loading 族——而 loading
  落地后仍然缺三样本能力：改文案、改终态类型、改时长。也就是说新增一族
  API 并没有消掉对「可更新」的需求，只是把需求藏进了 loading 里，还多
  了一份要并行维护的语义。做成通用能力后，进度卡只是第一个使用者。
- **靠「关掉旧的、再发一条新的」模拟更新**：这是现状的做法。每改一次
  文案就是一次关闭加一次创建，卡片闪一下、位置重排一次，而且新消息可能
  触发淘汰，把正在显示的另一条挤掉。它把「同一条消息在演进」表达成了
  「一串不同的消息」，与用户看到的东西不符。
- **用 `duration: Infinity` 表示常驻**：`Infinity` 会被当成一个数值参与
  校验与比较，容易出现「很大所以约等于永不关闭」这种含糊判定，还要处理
  序列化与显示。`0` 是约定的哨兵值，含义单一、判定直接。
- **常驻消息完全不计入条数**：实现最省事，但页面消息总量就失去了可预期
  的上界——常驻卡越多，普通消息的名额越说不清。计入条数、豁免淘汰，两个
  目标都保住了。
- **全部常驻时仍强行关闭最旧的**：会把「所有卡片都在用」这种合法状态判成
  超限，用户看到卡片无缘无故消失。这条与「常驻不该被静默清掉」直接冲突，
  只能接受同屏超过 3 条。

## 为什么不改 `Message.position`

位置不参与更新，是有意为之，不是遗漏。

改位置不只是改一个样式属性：消息是按位置分组堆叠的，每条卡片的位置偏移
由「同组内它前面那些卡片的高度之和」算出来。一条消息换组，等于从旧组拔
走、往新组插入，两组都要重排——旧组要补上空隙，新组要把它以及它后面的
卡片整体下移（或上移）。这批联动逻辑与「更新文案、更新类型」完全不是一
个量级，而且真正需要挪位置的场景至今没有出现：进度卡从出现到消失都在同
一个角落。

把它排除在更新之外，代价是调用方若要换位置就得关掉重发——与现状一致，
没有变差；收益是更新这件事保持在「改这一张卡自己」的范围内，不必引入跨
卡片的重排事务。如果以后真的出现必须在存续期间挪位置的场景，再单独立一
条决策来补，而不是顺手塞进更新里。
