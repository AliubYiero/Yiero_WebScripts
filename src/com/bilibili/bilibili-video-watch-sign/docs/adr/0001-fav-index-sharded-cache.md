# 0001 收藏夹索引分片缓存

- Status: accepted
- Date: 2026-11-08

## Context

脚本判断「视频是否已收藏」靠一整份收藏夹索引，而不是逐条请求
收藏状态接口。索引要跨页面、跨会话复用，因此落在 GM 存储里。

旧实现把每个收藏夹的全部条目（`IFavResourceId`，含 bvid、标题、
封面等字段）塞进单个 `favIndexCache` JSON。两个后果：

- 体积大。一条记录约 72 字节，2 万条约 1.4MB，而判断「是否收
  藏」其实只需要 aid。
- 写入放大。`GM_setValue` 是整值覆盖，而刷新循环里每个收藏夹都
  persist 一次，30 个夹就是 30 次全量重写，再加循环外一次。

此外缓存只按「当前 mid」判断能不能用：换账号后旧账号的键既不会
被覆盖，也不会被回收，多人登录会无限堆叠。v1 布局也没有需要保留
的历史包袱。

## Decision

### 只存 aids

持久化的索引只保存 `number[]` 形式的 aid。查询时把 BV 号用本地
`bv2av` 解码成 aid 再查集合；解码后用 `av2bv` 回环校验，回环不
一致视为无法解析，避免拿垃圾数字去查。这样去掉了 bvid 集合，体
积约为双集合方案的一半。

### 分片布局

| 键 | 值 | 写入时机 |
| --- | --- | --- |
| `favIndex:meta:<mid>` | `IFavIndexMeta` | 每轮同步末尾一次 |
| `favIndex:aids:<mid>:<folderId>` | `number[]` | 该夹内容变化时 |
| `favIndex:mids` | `number[]` | 新增或回收 mid 时 |
| `favIndexCache` | v1 旧键 | 首次加载即删 |

`folderId` 用收藏夹的 `media_id`，与收藏夹页 URL 的 `fid` 相同，
且在跨页范围内唯一。manifest 里每个夹记录 `id`、`fid`、`title`、
`mediaCount`、`itemCount`、`aidCount`、`synced`；分片里另存同一
份 `itemCount` 与 `mediaCount`，因为分片可能比 manifest 旧。

### 完整性用 itemCount 判定

`mediaCount` 是收藏夹全部类型条目数（视频、音频、合集），而 aids
只收 `type === 2` 的视频。所以不能用 `aidCount === mediaCount`
判断完整，必须用 `itemCount === mediaCount`；`aidCount` 只用于
诊断。某个夹的 `resource/ids` 拉取失败时，保留旧分片与旧计数，
标 `synced: false`，整份索引降级为不完整。

### 不迁移，立即删旧键

升级后首次加载发现 `favIndexCache` 就删掉，不读、不迁移，然后重
拉网络。一次性布局变更不值得写迁移路径，双份存储也不该常驻。已
知代价：升级后第一次同步若撞上风控或断网，用户会暂时退回「无缓
存、无标记」，只留一条 `console.info`。

### 按 mid 命名空间，切换即回收

分片键都带 mid。加载时先读 `favIndex:mids`，对除当前 mid 外的
每个 mid：读 manifest，逐个删 aids 分片与 manifest，再从注册表移
除。只保留当前账号的缓存，不做多账号共存。

## Consequences

- 写一个夹只写一个分片，单次写入与收藏夹数量解耦；首次读盘变成
  N+1 次（1 份 manifest + 每夹一个分片），靠 5 分钟 TTL 复用摊
  薄。
- 体积从约 1.4MB 降到约 0.2MB 量级（2 万条 aid 的 JSON 数组），
  仍随收藏总量线性增长。
- 失去 bvid 直接匹配：任何 videoId 都要先解码，解码失败归为
  `unparsable`，不回源。
- 升级后的首次同步失败会短暂失去索引；之后每次成功同步都会自
  愈。
- 切换账号会删掉其它 mid 的缓存，切回去要重拉一次。
- 注册表与分片键可能不一致（写失败、手动清键）。注册表丢失时孤
  儿分片不会被回收，只占空间，不影响判定；下次写入同一 mid 会重
  新登记。
- 缺分片的夹按「未同步」处理，不能当成空收藏夹，否则会把整夹视
  频误标为未看。

## Alternatives considered

- **aids + bvid 双集合**：查询不用解码，但体积约 2 倍，而 BV 解
  码是纯本地算法，没有换取的必要。
- **保留 items 对象、只做分片**：分片解决了写入放大，单条 72 字
  节的体积与冗余字段仍在。
- **单键存全量 aids**：体积降了，但每次写仍全量覆盖，核心问题没
  解决。
- **aids 存逗号分隔字符串**：再省一点，但多一层解析与容错，收益
  不抵复杂度。
- **读时迁移 v1**：多一条长期维护的路径，为一次性升级不值得。
- **保留旧键一段时间**：双份存储常驻，且没人知道哪份是权威的。
- **保留其它 mid 的缓存 / 只留最近 2 个**：前者无限堆叠，后者多
  一段回收逻辑；当前只服务当前账号，直接全删最干净。
- **用 `GM_listValues` 枚举 mid**：它返回的是本脚本全部 value
  键，不是「索引拥有哪些 mid」，回收时要遍历并解析键名前缀，还
  得处理解析失败与别的前缀；不同脚本管理器对它的实现也不完全一
  致。显式注册表只多一次小读取，却让「删除某个 mid 的全部键」有
  确定答案，也让存储层不依赖枚举 API。

## 两个非显然点

### 为什么 aids-only 还要 itemCount

完整性校验比较的是「本地实际拿到的条目数」与「远端声明的条目
数」。远端 `mediaCount` 计的是全部类型（视频、音频、合集），而
aids 只保存视频。夹里只要有音频或合集，`aidCount` 就永远小于
`mediaCount`；若拿它判完整，索引会长期被判为不完整，所有未命中
的视频都会转成逐条回源——这正是本次要消除的级联。所以必须另存
一个覆盖全部类型的 `itemCount` 来比较，`aidCount` 只留作诊断。

### 为什么用 favIndex:mids 而不是 GM_listValues

`GM_listValues` 的语义是「脚本的所有存储键」，而我们需要的是
「收藏夹索引拥有哪些 mid」。用前者意味着每次加载都遍历全部键、
按前缀解析、跳过解析失败项，既慢又把键格式变成隐式契约。显式注
册表把所有权写进数据本身：读一次就知道要回收谁，删某个 mid 的
全部键不需要枚举存储，也不受各管理器对 `GM_listValues` 实现差异
的影响。代价是注册表与分片可能不同步，但那只产生孤儿键，不影响
正确性。
