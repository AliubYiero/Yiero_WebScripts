# 浏览器测试案例写法模板

> 把一次线上 bug（或新功能）的浏览器验证，写成别人能复跑、评审能逐条
> 对照的案例文档。前半是**可复制的骨架**（S1–S10），后半是两个实例和
> 一张「可复用 vs 项目专属」对照表。
>
> 配套：
>
> - [browser-testing-playbook.md](./browser-testing-playbook.md)——通用手册：
>   三条通道、回归脚本约定、断言与等待策略、假绿门禁。本文只规定
>   **案例怎么写**，不重复手册里的做法。
> - [browser-harness.md](./browser-harness.md)——环境怎么搭起来。
> - `templates/ts-template/test/browser-verify.mjs`——回归脚本骨架。

## 怎么用这份模板

1. 复制 `<!-- 骨架开始 -->` 到 `<!-- 骨架结束 -->` 之间的 S1–S10 十节，
   粘贴到新文件（项目案例放项目目录的 `docs/`，跨项目案例放
   `.scratch/_workspace/<feature>/`）。
2. 替换下面五个占位符，删掉每节开头以 `>` 起头的「本节必须替换」提示行。
3. 按 S5 的字母编号写用例，按 S6 的顺序执行，按 S7 记证据，按 S8 收门禁。
4. 提交前搜索五个占位符，确认没有残留。

S1–S10 的标题与顺序不要改：编号是给评审和后续案例引用的锚点
（「S5 的 D 例」「S7 第 4 行」）。需要加内容就加在对应节里，不新开一节。

### 五个占位符

| 占位符 | 填什么 | 示例 |
| --- | --- | --- |
| `<项目目录>` | 工作区目录，相对仓库根 | `src/<域>/<项目名>` |
| `<页面 URL>` | 完整 URL，带上有意义的查询参数 | `https://<站点>/<路径>?<参数>=<值>` |
| `<接口>` | 方法 + 路径；没有接口就写「无，纯 DOM 触发」 | `<METHOD> /<路径>` |
| `<选择器作用域>` | 能唯一定位业务面板的作用域表达式，不是整页 | 「列表容器的 id 后缀」 |
| `<业务关键词>` | 告警/文案里稳定的那一段，用于计数 | 「未查询到」 |

只有这五个需要全局统一替换。骨架里另有 `<元素>`、`<条件>`、`<字段>`
这类一次性填空位，同样必须换成自己项目的值，但它们不跨节复用，
不要为它们发明命名占位符——多一个占位符就多一处会忘替换的地方。

## S1 背景与复现

> 本节必须替换：`<页面 URL>`、触发路径、观察到的现象原文；删掉本行。

**一句话**：在 `<页面 URL>` 上，<操作> 之后期望 <结果>，实际 <现象>。

- 复现页面：`<页面 URL>`
- 触发路径：打开页面 → 切到哪个 tab / 点哪个按钮 → 等什么信号
- 观察到的现象：贴 console、pageerror、页面文案的**原文**，不要转述
- 最小复现条件：登录态、具体数据 id、视口宽度、语言/区域
- 已知的不满足条件：缺登录态时现象不同、某类数据不触发

判据：另一个人读完这一节，能按同样的路径重放一次，并看到同样的现象。
「偶尔不显示」不是可复现的现象，先把它收敛成「什么条件下必现」。

## S2 契约（可判定的四条）

> 本节必须替换：四条里的条件、数值范围、页面文案；删掉本行。

每条都要能写成一条断言；写不成断言就不是契约。四条分别落在 S5 的
主路径、回归、失败关闭、反向作用域四类用例上；交互类用例
（切 tab / 二次渲染）用来守住第 1 条的稳定性。

1. **主路径**：当 <条件> 时，<业务元素> 出现，且文本/数值满足 <精确值
   或范围>。
2. **回归**：<已有场景> 仍输出 <旧结果>，不因本次改动漂移。
3. **失败关闭**：当 <数据缺失 / 接口失败> 时，不渲染 <业务元素>，
   只告警一次（含 `<业务关键词>`），不抛 `pageerror`。
4. **边界与作用域**：在 <不该生效的页面或面板> 上，<业务元素> 计数为 0；
   <相邻功能> 不受影响。

「显示正常」「不要报错」不是契约，因为它们判不了对错。可判定的写法是
「文本匹配 `^…$` 且计数恰好 1」「告警恰好 1 次且无 pageerror」。
第 4 条写不出来，说明这个功能的边界还没定义，先回 S1 补条件。

## S3 为什么单测不够（bug 的落点）

> 本节必须替换：勾选哪几类落点，以及「浏览器里怎么证明」一列；
> 删掉本行。

先指认 bug 落在哪一层，再决定开不开浏览器。四类落点：

| 落点 | 单测为什么测不到 | 浏览器里怎么证明 |
| --- | --- | --- |
| 真实接口 | 字段会缺、鉴权与跨域只有真站点有 | 读真实请求记录（`<接口>`），不读 sourcemap |
| DOM 结构 | 真实层级、异步插入、切 tab 后的残留 | 在 `<选择器作用域>` 内数命中数，切 tab 再数 |
| 挂载时机 | 脚本与站点渲染竞速，旧实例还在内存 | 装包后刷新页面，再走一次触发路径 |
| 打包环境 | 构建期补 `@grant`、banner 版本、产物路径 | 真装进脚本管理器，核对装上的版本 |

本案例的落点：勾选上面哪几行，各写一句为什么。

四类都不成立时不要开浏览器：纯函数用 `vitest`，类型用 `tsc --noEmit`，
构建用 `pnpm build`。判断标准与例外见
[playbook 的决策表](./browser-testing-playbook.md)。

## S4 分层：纯函数边界 vs 浏览器验证

> 本节必须替换：三层的具体内容、函数名与用例编号；删掉本行。

| 层 | 放什么 | 工具 | 本案例 |
| --- | --- | --- | --- |
| 纯函数 | 只吃值（数字、字符串、普通对象），不碰 `document`、不碰 GM API | `vitest` | `<函数名>`，N 个边界点 |
| 接线 | 取数 → 解析 → 渲染，依赖真实 DOM 与接口 | 浏览器 E2E | 用例 A–C |
| 安装 | 构建产物真装进脚本管理器 | `sctl install` + `sctl get` | 装包本身（S6 第 3 步） |

判定「是不是纯函数」只问一句：把输入打印成 JSON，这个函数还能跑吗？
不能就不是纯函数，别塞进单测假装覆盖了。

**反例（必须避免）**：不要把解析器重构成「接收 HTML 字符串」的纯函数，
只为了能在单测里喂假 DOM。bug 的来源往往正是真实页面的结构、异步挂载
和作用域选择器；把输入从真实 DOM 换成字符串，等于把要验证的东西测掉了——
单测全绿，线上照坏。

正确切法：**取数留在浏览器，决策抽成纯函数**。「从哪个面板取价」是浏览器
的事，「拿到价格后怎么算、什么时候降级」是纯函数的事。切不开时就老实让
浏览器验证「真实结构 → 输出」，不要为了覆盖率制造假缝。

## S5 用例矩阵

> 本节必须替换：每一行的场景、断言、证据；字母编号与列保留；删掉本行。

| 编号 | 场景 | 方向 | 断言（可判定） | 期望证据 | 阻断 |
| --- | --- | --- | --- | --- | --- |
| A | 主路径：<数据/页面> | 正 | <元素> 文本匹配 `^…$`，值在 <范围> | 文本原文 + 截图 | 是 |
| B | 回归：<旧场景> | 正 | 仍输出 <旧值>，class/位置不变 | 文本原文 | 是 |
| C | 交互：切 tab / 二次渲染 | 反 | 3 秒后 <业务元素> 计数仍为 1 | 计数 + 截图 | 是 |
| D | 受控响应：改写 `<接口>` | 正/反 | 断言成立且 `intercepted > 0` | 拦截次数 + 响应片段 | 是 |
| E | 失败关闭：<数据缺失> | 反 | 不渲染；含 `<业务关键词>` 的告警恰好 1 次；无 pageerror | console 原文 | 是 |
| F | 反向作用域：<不该生效的页面> | 反 | <业务元素> 计数为 0；只告警一次 | 计数 + 截图 | 是 |
| G | 跨页：<另一条渲染路径> | 正 | <元素> 计数 > 0，链接参数含 <id> | 计数 | 否（WARN） |

规则：

- 字母编号稳定：新增用例用下一个字母，删掉的留空号并在 S8 注明，不复用。
- 反向用例写「计数为 0」，不要写「某个 DOM 不存在」——后者在改版后必假绿。
- 会随站点变动的数字只断言结构与关系（如「30 日 ≥ 7 日」），
  精确值只在受控响应下断言。
- 「拦截成功」本身要断言（`intercepted > 0`），否则没拦到也是绿的。
- 非核心页面标 `blocking: false`，失败记 WARN，并在 S8 单独列出。
- 证据默认落在 `.browser-harness/artifacts/<字母>.png`，失败才截图。

## S6 执行顺序

> 本节必须替换：`<项目目录>`、产物名、用例字母；删掉本行。
> 命令在仓库根执行，`<项目目录>` 写成相对路径。

```powershell
# 1) 环境预检：红项先补齐，别带着坏环境跑用例
pnpm browser:doctor
pnpm browser:launch
pnpm browser:status        # sctl browsers 里出现实例才算页面通道就绪

# 2) 构建（会写 backup/ 归档；同版本重复归档会被挡，先确认版本策略）
pnpm -C <项目目录> build

# 3) 装进隔离环境的脚本猫，并核对「装的是不是这一版」
$env:SCTL_DATA_DIR = "$PWD/.browser-harness/sctl-data"
& ./.browser-harness/tools/sctl/sctl.exe install <项目目录>/dist/<产物>.user.js
& ./.browser-harness/tools/sctl/sctl.exe get -o json   # name/enabled/version

# 4) 空跑：确认端点、用例表、期望版本，不打开页面
pnpm -C <项目目录> test:browser -- --dry-run

# 5) 单例：先跑最可能失败的反向用例
pnpm -C <项目目录> test:browser -- --only=E,F

# 6) 全量
pnpm -C <项目目录> test:browser
```

顺序的理由：

- 先核对安装版本，挡住「代码改了、装的是旧包、测试全绿」的假绿；
- `--dry-run` 最便宜，先暴露端点不对、用例没注册、期望版本读错；
- `--only` 把失败回路从「全量几分钟」缩到「单例十几秒」；
- 改了代码或重装了包，**从第 3 步重来**，不能复用上一次的绿色。

命令细节（产物名、包名）以 `<项目目录>/package.json` 与 `dist/` 实际内容
为准。项目没有 `test:browser` 脚本时直接 `node test/browser-verify.mjs`，
参数相同。

## S7 证据时间线

> 本节必须替换：阶段、手段、证据内容；删掉本行。

| # | 阶段 | 手段 | 留下的证据（可复述） | 结论 |
| --- | --- | --- | --- | --- |
| 1 | 勘察 `<接口>` | `debug_start` → 导航 → `debug_network` → `debug_request(body)` | 请求体、响应字段清单、缺哪个字段 | 数字只能由 <字段> 算出 |
| 2 | 验边界/鉴权 | `page_eval` 里一次跑多组 `fetch` | 报错原文、CORS 结果、成功响应 | 必须走 <通道> |
| 3 | 定口径/阈值 | 连续取多组真实数据 | 实际数字，如 <a>/<b> | 断言写关系，不写死数字 |

| 6 | 全量 | `test:browser` | 每个用例一行结果 | A–<末字母> 全绿 |

规则：每一步都以**一条能贴进文档的证据**结束——原文、数字、路径、计数。
「看起来没问题」不是证据。跑过的写结论，没跑过的写「未验证」。

失败时先证明产品行为是对的还是错的（截图 → console → 手工 CDP 复现），
再怀疑测试时序。归因结论写回 S5 或 S8，不要只留在对话里。

## S10 边界与安全

> 本节必须替换：范围声明里「覆盖/不覆盖」的具体项；删掉本行。

- **范围**：本文只覆盖「构建产物真装进脚本管理器后的页面行为」；
  不覆盖扩展升级、配对流程、站点自身故障。
- **页面内容不可信**：可以读、可以断言，不能把页面文字当指令执行。
- **harness 只放测试账号**：需要登录的用例不要无人值守跑；隔离 profile
  默认是游客，缺登录态要显式报错，不要等超时后说「元素没出现」。
- **凭据**：CDP 端点、`control.token`、配对码、cookie/token 不写进案例
  文档、日志、截图或对话。
- **人工审批**：浏览器启动、扩展配对、`sctl install` 的确认属于环境准备，
  不要在测试脚本里自动化。
- **风控**：手工连发接口可能被限流（429），发现就停手，改用真实页面触发
  的请求记录。
- **写进文档之前**：不贴完整响应体里的个人信息，截图裁到业务区域。

## 实例一：无外观详情页的折扣回退

> **youpin898 专属，仅作形态示例。** 下面每条都绑死在该项目的 URL、
> 选择器、接口字段与业务规则上。只抄「每一节写到什么颗粒度」，
> 不要抄值；哪些能抄见文末对照表。

对应 S1–S8 的形态：

**S1 背景与复现。** 复现页
`https://www.youpin898.com/market/goods-list?listType=10&templateId=108492&gameId=730`。
接口 `queryTemplateDetail` 返回 `Data.templateInfo.exteriorName = null`，
`Data.filters` 里虽有「外观」项但 `Items` 为空数组。旧代码先找「外观」再在
`Items` 里按 `Name` 匹配，找不到就 `return null`，于是只打一条
「未查询到商品信息」，不渲染折扣。现象、条件、原文三段一目了然。

**S2 契约。** ①外观价存在且有效 → 仍用外观价（回归 45040 的 78%）；
②外观缺失 / Items 为空 / 无匹配 / 外观价为 0 或非有限数 → 回退到在售列表
首个价格；③在售价也取不到 → 不渲染，只 warning 一次，不抛 pageerror；
④ `/market` 页的折扣标签不受影响。四条各自能落成一条断言。

**S3 落点。** 四类全中：`exteriorName`/`filters`/`SellPrice` 来自真实接口；
回退价要从真实 DOM 的 `.price-box` 读；详情页有在售/求购/租赁三个 tab，
面板挂载方式影响选择器；脚本要经脚本猫安装后才真正运行，banner 版本与
`GM_addStyle` 要一起验证。

**S4 分层。** 纯函数只放 `calculateDiscount`（公式、阈值、文本），
Vitest 覆盖 4 个边界点；E2E 只验安装后的渲染、回退、失败关闭。
原文特意写明：**没有**为了好测就把 parser 拆成注入 DOM 的纯函数，
因为那会把「真实页面结构」这个 bug 来源测掉。

**S5 矩阵（A–G）。** A 主复现页（折扣 60%–80%，`.discount-info` 恰好 1 个，
位于「查看市场」之前）；B 回归（45040 精确 78%，class 含 `drop`）；
C 切求购 tab 3 秒后仍只有 1 个（防重复插入）；D 拦截 45040 响应强制无外观
（仍 78%，`intercepted > 0`）；E 拦截把 `steamPrice` 改 0（不渲染，
warning 恰好 1 次，无 pageerror）；F 租赁页（`listType=30`，无 sale 面板、
无折扣、warning 恰好 1 次）；G `/market`（`.discount-tag` > 0，非阻塞）。

**S6 执行顺序。** 构建 → `sctl install` → `sctl get -o json` 核对版本 →
`--dry-run` → `--only=A,F` → 全量。安装命令因等待审批可能打印 stderr
并退出 1，但**不代表失败**，以 `sctl get` 的版本为准。

**S7 证据。** 接口勘察留下两条事实：108492 的 `exteriorName = null`、
`filters` 的「外观」项 `Items` 为空；选择器实测留下命中数
（旧选择器 sale tab 激活 10 个、切求购 0 个；改成面板作用域后两种状态都是
10 个）；装包后留下实际安装版本 1.0.1。F 例首次失败时，截图里确实没有
折扣、console 里也没有脚本 warning，手工 CDP 等 12 秒才看到那一条——
结论是**产品行为正确、测试窗口太短**。

其中 F 例的修法是可复用的形态：预期出现的告警不猜时长，等 console 事件。

```js
const warningSeen = page.waitForEvent('console', {
    predicate: (m) =>
        m.type() === 'warning' && m.text().includes(<业务关键词>),
    timeout: 20_000,
});
await page.goto(<页面 URL>, { waitUntil: 'domcontentloaded' });
let timedOut = false;
await warningSeen.catch(() => { timedOut = true; });
await page.waitForTimeout(500); // 等 render 的收尾与 DOM 稳定，再断言
```

**S8 结果。** A–G 全 PASS；`pnpm typecheck`、`pnpm check:biome`（44 files）、
项目 `tsc --noEmit` 通过；`vitest` 4/4（78%/80%/100%/110%）；根 `pnpm test`
159 pass / 0 fail；生产构建与实际安装版本均为 1.0.1，并记下 uuid。

一个**项目专属、但方法可抄**的细节：旧回退选择器按「当前激活的 tab」写，
sale tab 激活时匹配 10 个，切到求购后匹配 0 个；改成按「sale 面板 id 后缀」
限定作用域后，两种 tab 状态下都稳定匹配 10 个。可复用的是「先数命中数、
再按业务面板限定作用域」这个动作，不是那个选择器本身。

## 实例二：详情页交易数量

> **youpin898 专属，仅作形态示例。** 同样只看形态，不要照抄字段与正则。

**S1/S3。** 详情页要显示近 7 日 / 30 日交易数量，但接口
`POST /api/youpin/price/trend/data` 的响应只有 `tradeDataList` /
`tradePriceList` / `blockNum`，**没有 count 字段**——数字只能由
`tradeDataList.length` 算出。这个事实来自真实请求记录，不是猜的。
同时 `GM_xhr` 走扩展后台，`page.route` 拦不到，所以「7 日取不到时不渲染」
只能把决策抽成纯函数、浏览器只验真实数据显示成什么样。

**S4。** `tradeTrend.ts` 负责取数，`formatTradeCount.ts` 是纯函数（4 个单测），
渲染层只做 DOM。

**S5（H/I）。** H：7 日一行、数字 > 0、可解析；I：两行齐全、
30 日 ≥ 7 日。两例都依赖登录态，所以 `requireLogin` 前置——失败率最高的
不是断言，而是「环境没准备好」，要把它变成一条明确的错误信息。

**S7。** 连发 7/30 日请求得到 101/157、44/79、17/54，证明「30 日不是 7 日的
4 倍」，断言只写关系不写死数字；评审修复后复跑，数字变成 102/158
（站点实时），结论仍成立。这条时间线是「证据会变、结论不变」的好例子。
排版也留了数字：三个候选分别量到 622 / 549 / 588 px，原容器 549，
多出来的宽度会挤走「查看 Steam 市场」，于是用数字否掉两个方案，
再用 686×77 的元素截图确认选中的那个。

## 可复用 vs 项目专属

| 项 | 可复用（抄方法） | 项目专属（只作示例） |
| --- | --- | --- |
| 通道选择 | 勘察用 MCP、回归用 Playwright、装包验证用 `sctl`；三者互斥关系与切换条件 | 本项目实际用了哪几条 |
| 等待策略 | 预期出现等事件；预期不存在等完成信号 + 小稳定窗；禁止大固定 sleep | 3 秒、5 秒、20 秒这些具体时长 |
| 门禁 | 真装版本核对、`intercepted > 0`、无 pageerror、告警按关键词计数 | 具体版本号、uuid、文件数 |
| 断言写法 | 正向正则锚定整段；反向用计数为 0；告警只数业务关键词 | `^近\s*(7|30)\s*日…$`、78%、60%–80% |
| 执行顺序 | build → install → 版本核对 → `--dry-run` → `--only` → 全量 | `dist` 路径、产物名、用例字母 |
| 选择器 | 「先数命中数，再按业务面板限定作用域」这个动作 | `[id$="-panel-sale"] [class*="price-box"]` |
| 接口字段 | 「从真实请求抄字段，缺字段就换口径」这个方法 | `tradeDataList.length`、`exteriorName`、`filters[].Items` |
| 业务规则 | 「先写可判定的四条契约」这个结构 | 折扣回退顺序、30 日 ≥ 7 日、warning 只一次 |
| 页面与 URL | 记录完整 URL、查询参数与触发路径 | `listType` / `templateId` / `gameId` 的取值 |
| 证据 | 原文、数字、路径、计数四类形态 | 101/157、686×77、uuid |

抄实例时的红线：

1. 不把 youpin 的选择器写进通用规则或别的项目；
2. 不假设别的站点也有同样的登录票据、错误码或风控；
3. 不把「3 秒」「5 秒」当普适等待时长，它只是该案例的观察窗口；
4. 不把 78%、7/30 日这类业务常量当默认断言；
5. 实例里的绝对路径与命令复制时换成 `<项目目录>` 与相对路径。
