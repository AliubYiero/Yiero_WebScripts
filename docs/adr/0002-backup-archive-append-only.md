# 0002 备份归档只追加，不覆盖

- Status: accepted
- Date: 2026-11-01

## Context

每个脚本项目的 `backup/` 目录保存发布产物与历史版本归档：

- `versions.json`：版本号 → 归档文件名；
- `<项目名>.zip`：全量归档；
- `<项目名>_<版本>.backup.js`：每个版本一个。

`@yiero/vite-plugin-scriptcat-backup` 在构建结束时检查当前版本是否已归档，已归档则直接抛错（错误消息为「脚本备份已存在, 请勿重复备份脚本」）。也就是说「同一版本只能归档一次」是插件契约，不是可选项。

这条契约与「一键构建全仓」天然冲突：全仓里绝大多数项目当前版本的归档都已存在，直接 `pnpm -r build` 会在第一个项目上失败。

## Decision

备份归档只追加、不覆盖，也不静默跳过。重复版本就是错误。

需要全仓验证构建时，用「快照归档目录 → 构建 → 还原归档目录」的方式绕开归档检查，而不是修改归档语义。发布产物的地址因此保持稳定，历史版本始终可回查。

## Consequences

- 全量验证构建必须实现原子还原——构建失败时同样要还原，否则仓库留下半截归档。
- 「版本号变了」是唯一合法的发版动作；构建命令只能靠「当前版本 vs 归档记录」判断是否待构建。
- 构建命令不能靠给插件打补丁来获得强制覆盖能力，否则跨版本升级时会重新引入风险。
- 归档目录的内容被视为可验证的契约：全量验证构建前后必须逐字节一致。

## Alternatives considered

- **让构建覆盖同名归档**：破坏「用户装到的是哪个版本」的可追溯性，也破坏已入库发布产物的稳定性。
- **给第三方插件加 `force` 选项**：需要 fork 或补丁依赖，跨版本回归风险高，且把「归档不可变」这条领域规则降级成配置项。
- **允许静默跳过已归档版本**：结果是一键构建看起来成功、实际什么都没构建；这正是当前没人敢用全仓构建的原因。
