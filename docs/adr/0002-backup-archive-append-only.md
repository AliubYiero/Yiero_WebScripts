# 0002 备份归档只追加，不覆盖

- Status: accepted
- Date: 2026-11-01
- Revised: 2026-11-10 —— 决策本身不变（归档只追加），但绕开归档检查的
  做法改了：原先「快照 → 删掉整个 `backup/` → 构建 → 合并还原」会
  让插件拿不到旧 zip，重建后的 zip 只剩当前版本，同时把
  `backup/<项目名>.user.js` 的 mtime 刷新成构建时刻。改为「只摘掉当前
  版本的登记、保留 zip」，并按「该版本原本是否已归档」无条件还原。

## Context

每个脚本项目的 `backup/` 目录保存发布产物与历史版本归档：

- `versions.json`：版本号 → 归档文件名；
- `<项目名>.zip`：全量归档；
- `<项目名>_<版本>.backup.js`：每个版本一个。

`@yiero/vite-plugin-scriptcat-backup` 在构建结束时检查当前版本是否已归档，已归档则直接抛错（错误消息为「脚本备份已存在, 请勿重复备份脚本」）。也就是说「同一版本只能归档一次」是插件契约，不是可选项。

这条契约与「一键构建全仓」天然冲突：全仓里绝大多数项目当前版本的归档都已存在，直接 `pnpm -r build` 会在第一个项目上失败。

## Decision

备份归档只追加、不覆盖，也不静默跳过。重复版本就是错误。

需要全仓验证构建时，用「快照归档目录 → 只摘掉当前版本的登记 → 构建 → 还原归档目录」的方式绕开归档检查，而不是修改归档语义。发布产物的地址因此保持稳定，历史版本始终可回查。

关键是**只摘登记、不删 `<项目名>.zip`**：插件会读盘上已有的 zip 再往里追加，所以重建时历史归档仍在；若像早期实现那样先把整个 `backup/` 删掉，插件就拿不到旧 zip，新 zip 里只剩当前版本。已归档版本的重建结果一律整体还原（含文件修改时间），因此全量验证构建不会改写任何既有归档，也不会刷新 `backup/<项目名>.user.js` 的 mtime。

## Consequences

- 全量验证构建必须实现原子还原——构建失败时同样要还原，否则仓库留下半截归档。还原先把快照复制到同级暂存目录再换名，复制失败时原目录仍在。
- 还原必须连修改时间一起还原：`backup/<项目名>.user.js` 的 mtime 是 `pnpm update:readme` 在 `getLastUpdateWay: 'file'` 下的「最后更新」来源，校验性重建刷新 mtime 会让 README 里的更新日期凭空变成今天。
- 摘登记与还原之间若被强杀（SIGKILL、断电），当前版本会停在「未登记」状态；SIGINT/SIGTERM 已由构建命令接管回滚，其余情况靠一次正常构建补齐。
- 「版本号变了」是唯一合法的发版动作；构建命令只能靠「当前版本 vs 归档记录」判断是否待构建。版本号变了就是真发版，此时改写归档是这个动作本来的目的，不受上述还原约束。
- 构建命令不能靠给插件打补丁来获得强制覆盖能力，否则跨版本升级时会重新引入风险。
- 归档目录的内容被视为可验证的契约：全量验证构建前后必须逐字节一致。实测工具链升级会让同一版本重新构建产出不同字节，因此「产物没变才还原」不足以保证契约，必须按「该版本是否已归档」无条件还原。

## Alternatives considered

- **让构建覆盖同名归档**：破坏「用户装到的是哪个版本」的可追溯性，也破坏已入库发布产物的稳定性。
- **给第三方插件加 `force` 选项**：需要 fork 或补丁依赖，跨版本回归风险高，且把「归档不可变」这条领域规则降级成配置项。
- **允许静默跳过已归档版本**：结果是一键构建看起来成功、实际什么都没构建；这正是当前没人敢用全仓构建的原因。
